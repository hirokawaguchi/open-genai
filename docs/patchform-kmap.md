# 手続き定義の将来拡張（KMAP）

手続きマスタが将来読める与件と、そこに至る順序である。いまの画面と API の説明は [patchform.md](patchform.md) に書く。

完全系の文章はコードコメントに写さない。将来のキーを足す変更は、この文書の「道筋」を同じ変更で更新する。文書に無いキーは読まない。文書にあってコードに無いキーは未実装である。

## 完全系

申請手続の書類関係は、法令上の与件として書く。エンジンは、確定した与件から転記候補と作業順を計算する。項目名が似ていることや、行データの推定や、モデルの出力を、そのまま与件にはしない。

決まったことは次のとおり。

- 証明書（住民票、登記事項証明書など）は手続の外に一度だけ書き、何を証するかを語彙と役割で持つ。手続は名前と役割を渡して添付する。項目一覧を手続へ書き写さない。
- 写してよい関係（参照）は、人が確定した辺だけである。語彙が同じだけでは辺にしない。本店の住所と代表者の住所、別人の氏名は、役割が違うので写し先にしない。転記は自動では書き込まず、候補を出して申請者が採否を決める。
- 手続の結果が、どの証明書で裏づくかを書く。後の手続がその証明書を添付しているとき、エンジンが先行関係にする。順序を「の後」とは書かない。
- 押印は、誰が押すかだけを与件にする。空欄のうちに押さないこと、同じ人が押す書類が揃ってから押すことは、エンジンの規則にする。
- 進行中の申請は、計画した手続の版と、そのとき使った証明書の版に結び付けたままにする。マスタを直しても、その申請の与件は変えない。
- 保存形式の標準は、YAML の字下げではなくキーの意味である。ファイルをまたぐ読み込みは、このエンジンのキー（証明書を名前で解決する）で行う。

まだ決めないことは、完全系にキーを足す理由にはしない。

- 作業順の計算を、参照グラフの重みとクリティカルパスのどちらにするか。
- 作業時間の見積り。論文の時間は仮説であり、定義には入れない。
- グラフの格納先。書類が数十の間は、計算と確認が先である。
- 条件の閉じた語彙。いま必要なのは「個人か法人か」と「役割の繰り返し」までである。資本金や支店の有無は、必要になったときに条件の種類を足す。
- エディタと、条文・様式からの下書き（コンバーター）の実装形態。下書きの参照は未確定のまま残し、人が確定した定義だけをエンジンが解釈する。

## 道筋

いま読むキーは、手続きの `mapping` だけである。意味は `patchform-app/app/procedure.py` の正規化が決める。

| キー | 意味 |
| --- | --- |
| `rules[].component_id` と `option` | 案内の、どの問いの、どの答えか |
| `rules[].form_ids` | その答えで出す様式 |
| `rules[].prepare` | その答えで出す添付の名前 |
| `rules[].notes` | 申請者への解説 |
| `rules[].refs` | 手引きの箇所などの文字列。写してよい辺ではない |
| `rules[].reviews` | その書類の形式検査と、受付が見る内容の確認 |
| `rules[].cross` | その答えの中で、書類をまたいで受付が見る確認 |
| `review` | 申請用紙が1枚のときの審査項目 |

形式検査の語彙は `file_present`（ファイルがある）、`pdf_or_image`（PDF または画像）、`issued_within_3_months`（発行日から3か月以内）だけである。発行日は受付が人で確認し、エンジンは判定しない。内容の確認は所見の文であり、合否は人の確定である。

提出で `applications.review_json` に審査項目を凍結する。手続をあとから直しても、その申請の項目は変えない。同じ語彙（`imi_type`）の欄へ記入候補を出す挙動は、フォーム側に残す。写してよい辺の代わりにはしない。

後続は、読む実装とテストが付いてからキーにする。空のキーは置かない。

1. 書き出し（`opengenai-patchform/export/1`）に、審査項目（`reviews`、`cross`、用紙1枚の `review`）を通す。いまの書き出しはこれらを落とす。
2. 同じ添付が複数の手続で繰り返されてから、証明書を手続の外に一度定義し、手続は名前で添付する。
3. 人が確定した写してよい辺を、既存の `refs` とは別のキーで足す。辺がある欄だけ、候補の根拠をその辺にする。
4. 役割の繰り返し（役員が複数なら、履歴書と住民票を組で足す）。
5. 手続の結果と、それを証する証明書から、手続をまたぐ先行関係を出す。

新しいキーを足すときは、正規化、書き出し、取り込み、テストを同じ変更に含める。いまの正規化は、知っているキーだけを残す。
